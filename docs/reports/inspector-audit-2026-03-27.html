3. Executive Summary

Top 5 findings an operator needs to know:

  1. Orchestrator submit has no atomicity (CHAOS-028, P1): If the status-update API call fails after the orchestrator run is already dispatched, the user sees a generic error and may re-submit, spawning duplicate orchestrator runs. The work is running but the UI says it failed.
  2. Image re-download loop doesn't check HTTP status (CHAOS-029, P2): When submitting to orchestrator, images are re-fetched from /uploads/. If any image returns 404, a 0-byte corrupt file is silently sent to the orchestrator with no error shown.
  3. Custom repo input is broken (CHAOS-032, P2): In FeatureRequestDetail, the "+ New repo..." custom input collects text but never writes it to selectedRepo. Work is always submitted to the previously-selected repo regardless of what the user types.
  4. Unvalidated repo/filename fields flow to orchestrator (SEC-030-033, P2): The repo, img.filename, and img.original_name fields pass through to the orchestrator without sanitization. If the orchestrator uses these in shell commands (e.g., git clone), command injection is possible.
  5. Test gaps on the actual fix (QA-001/002, P2): The repo field added to orchestrator submit is never asserted in tests. The BugDetail orchestrator submit path (the primary fix) has zero test coverage.

9. P1 Findings

P1 NEW CHAOS-028: Orchestrator Submit Has No Atomicity — Duplicate Runs on Partial Failure

File: BugDetail.tsx:94–120, FeatureRequestDetail.tsx:93–115

Exploit scenario: User clicks "Submit to Orchestrator." The orchestrator run is dispatched (step 1 succeeds). The subsequent bugs.update() status call fails (network error, backend restart, validation rejection). The catch block fires and displays "Failed to submit to orchestrator." The user believes submission failed and clicks again — spawning a second orchestrator run. The bug/FR status never updates to in_development.

Impact: Duplicate orchestrator runs waste compute. Bug/FR status is inconsistent with actual orchestrator state. User trust in the UI is degraded.

Recommendation: Separate the error handling: after orchestrator.submitWork() succeeds, status update failures should show a warning ("Submitted successfully but status update failed — please refresh") rather than a generic failure message. Never report a successful orchestrator dispatch as a failure.

P1 STILL OPEN SEC-001: Zero Authentication on All API Endpoints

File: Source/Backend/src/index.ts (no auth middleware)

Impact: Every API endpoint is open to anonymous callers. No JWT, no sessions, no user concept. All other P2 injection findings are amplified by this — attackers need zero preconditions to poison data.

15. Recommendations

This Sprint

  • CHAOS-029: Add if (!res.ok) check on image fetch in submit flow — prevents silent 0-byte files to orchestrator.
  • CHAOS-032: Wire customRepo input to setSelectedRepo — currently the custom repo feature is broken.
  • SEC-030/031: Sanitize img.filename and img.original_name before use in fetch URL and File constructor.
  • SEC-032/033: Validate repo field format (owner/repo or URL) both client-side and in the orchestrator proxy.
  • QA-001: Assert repo field in orchestrator submit test assertions.
  • CHAOS-030: Move onUpdate() call outside the try/catch block.

  • CHAOS-036: Add status update to batch submit path to match single-submit behavior.
